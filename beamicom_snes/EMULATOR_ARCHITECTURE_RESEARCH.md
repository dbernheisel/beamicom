# Architectural techniques used by mature SNES emulators

## Executive summary

Beamicom already uses several sound emulator techniques: deferred CPU timing, scanline-state capture, a phase-accurate 32-step S-DSP pipeline, frame reuse, per-render tile caches, and asynchronous PPU/DSP work. The largest remaining difference is the **shape of the hot core**, not a missing graphics or tensor algorithm.

ares, bsnes, Snes9x, and Mesen2 keep registers, RAM, clock debt, and intermediate pipeline state in compact mutable native structures. Their main loops mutate that state in place and synchronize components only when one component reaches another's clock or an observable event. Beamicom instead returns nested immutable CPU/bus/APU/PPU structs through almost every operation, stores major memories in Erlang `:array`, and sometimes reconstructs an exact APU timeline with event capture, dependency analysis, and replay. That preserves accuracy, but it makes the host representation substantially more expensive than the emulated work.

The highest-value accuracy-preserving direction is therefore:

1. Move one coherent hot ownership boundary—ideally CPU + bus + SPC700 + S-DSP, or at least SPC700 + S-DSP + shared APU RAM—into a mutable native resource called at coarse deadlines.
2. Replace APU event capture/replay with direct, cycle-ordered SPC/DSP mutation against the same RAM.
3. Specialize CPU/SPC opcode dispatch by mode and use direct page mappings for ordinary memory.
4. Keep decoded PPU tiles and flat VRAM/OAM mirrors alive across frames, invalidating only the written regions.
5. Use host parallelism only after causally relevant state has been captured: independent scanlines, presentation, audio delivery, and independent emulator instances.

Nx remains useful for large regular rendering kernels or a batch of independent consoles. It is not the architecture mature emulators use for the branch-heavy, dependency-rich CPU/SPC/DSP timeline of one console.

## What Beamicom is already doing well

- Its PPU raster/scanline capture is conceptually close to bsnes' fast renderer; replacing it wholesale would be unnecessary.
- Its 32-phase S-DSP implementation follows the same fundamental schedule used by ares, Mesen2, and snes_spc. [Mesen2 DSP schedule](https://github.com/SourMesen/Mesen2/blob/master/Core/SNES/DSP/Dsp.cpp#L248-L345)
- Its pending-clock accumulation and CPU polling-loop fast-forward already move toward deadline-based execution.
- It tracks VRAM generations and has full-frame reuse plus resident Nx caches. Those mechanisms can become the invalidation source for a longer-lived decoded-tile cache.
- It uses a reusable outer rendering worker, which is the right lifecycle; the remaining issue is per-frame row task creation and ephemeral worker-local caches.

## Recommended implementation order

### 1. Combine the APU hot core

Start with a native resource holding SPC700 registers, timers, DSP registers/pipeline, and the single 64 KiB APU RAM. Expose operations such as `run_to(clock)`, CPU-port read/write at a clock, drain PCM, and serialize/deserialize.

This boundary is small, testable against the existing DSP golden vectors, and directly eliminates dependency fencing and replay bookkeeping. Because SPC RAM reads/writes and DSP phases happen in one ordered transition, it should improve both accuracy confidence and throughput.

### 2. Introduce a compact event-deadline scheduler

Keep the current master-clock semantics, but represent the next few hardware deadlines in fixed fields. Run the CPU until the earliest deadline or MMIO interaction, service it, and continue. Synchronize the APU at CPU/APU port access and at bounded periodic deadlines, as Snes9x does, rather than routing every ordinary SPC access through a generic callback.

### 3. Specialize the 65C816 interpreter

Generate M/X mode-specific opcode handlers and select the table when REP/SEP/XCE changes mode. Add direct page descriptors for ordinary ROM/WRAM/SRAM access and a slow MMIO handler. This preserves every priced bus access while avoiding repeated width tests, region classification, and nested struct construction.

### 4. Make renderer caches persistent and incremental

Maintain a flat renderer mirror of VRAM/OAM and patch the written bytes. Persist decoded 8-pixel tile rows across frames and include the relevant page generation in each cache entry. Reuse a fixed row-worker pool instead of constructing tasks for every frame.

### 5. Consider a larger native machine core only after measuring

If CPU/bus struct churn remains dominant after the APU boundary and dispatch changes, expand the same native resource to the 65C816, bus, DMA/HDMA, and coprocessors. Keep Elixir as the orchestration, save-state, frontend, and testing layer. Cross the NIF boundary at a frame/event batch, not once per memory access or instruction.

## Approaches mature emulators suggest avoiding

- **Do not fuse PPU and APU into one Nx kernel.** They share master time but almost no data, and their observable interactions are sparse. A fused tensor graph pays for dynamic control flow and state transfer without creating useful SIMD work.
- **Do not put each emulated chip in an independently messaging BEAM process.** ares' “threads” are cooperative clock contexts with cheap shared native state; they are not comparable to frequent GenServer calls or messages.
- **Do not depend on inaccurate fast DSP/PPU modes to meet 60 FPS.** bsnes carries compatibility exceptions for its optional fast paths. The techniques above—mutable representation, deadline scheduling, dispatch specialization, and persistent caches—do not require an accuracy tradeoff.
- **Do not expect single-console CPU/SPC execution to batch well in Nx.** Batching becomes attractive across many independent emulator instances, where every lane can execute the same kernel without cross-lane dependencies.

## Bottom line

Beamicom is already close to mature emulators in *emulated algorithms*. It is farthest away in *host representation*: immutable nested values, persistent-array memory, repeated conversion, event logs, and task boundaries around small sequential work. The route to dependable 60 FPS is to make the exact machine cheaper to mutate, not to make more of the machine look like a tensor.
